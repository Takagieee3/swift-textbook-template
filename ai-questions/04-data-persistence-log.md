## 質問と回答の記録

### Q1

**質問：**

SwiftDataモデル（@Model）で構造体ではなくクラスで書く理由を教えて

**AIの回答の要点：**

メモリ上の実体を1つにするため（参照型）：
クラスは、データがメモリ上の「同じ場所」を指し示します。これにより、一覧画面（ContentView）と編集画面（MemoEditView）で同じ一つのメモを共有できます。

画面間での「自動同期」を実現するため：
もしこれが struct（値型）だと、編集画面に渡した瞬間に「コピー」が作られてしまうため、編集画面でタイトルを書き換えても一覧画面には反映されません。クラスだからこそ、編集画面での変更がリアルタイムにアプリ全体へ波及します。


**自分の理解：**

ContentViewとMemoEditViewで同じ一つのメモを共有するためまたリアルタイムで反映されないので画面間の
自動同期をさせるためにClassを使用する。

### Q2

**質問：**

構造体（Struct）ではデータがメモリ上の違う場所になるということですか

**AIの回答の要点：**

構造体を別の変数に代入したり、別の画面（View）に渡したりすると、メモリ上の全く別の場所に「まるごとコピー」が作られます。
```swift
// もしMemoが構造体（Struct）だった場合
var memoA = Memo(title: "買い物リスト") 
var memoB = memoA // ここでメモリ上の別の場所に「コピー」が作られる
// memoBを書き換えても...
memoB.title = "旅行の計画" 
// memoAは「買い物リスト」のまま（影響を受けない）
print(memoA.title)
``` 

**自分の理解：**

structを使用するとメモリ上でコピーが作られてしまい一覧画面に戻ったが古いまま変わらないという現象になる。今回の場合Classを使用することが良い。

**補足**

SwiftDataの@Model（クラス）を使うと、内部でデータが書き換わったら、それを表示しているすべてのViewに通知して強制的に再描画させるという特殊な仕組み（Observable）が自動で組み込まれます。
これにより、「メモリの同じ場所を書き換える（クラスのメリット）」と画面が自動で切り替わる（構造体＋@Stateのようなメリット)のいいとこ取りができるようになる。


### Q3

**質問：**

SwiftDataでは、画面に表示されている Memo という塊（オブジェクト）をそのままメソッドに放り込むだけで、裏側のデータベースが「あ、そのデータを処理すればいいのね」と自動で理解してくれます。このデータベース処理は自動で行われますが、自動の仕組みについて具体的に説明してほしい

**AIの回答の要点：**

1. ユーザーが削除を操作
      ↓
2. `modelContext.delete(memo)` が実行される
      ↓
3. SwiftDataが `memo` の裏に隠された「背番号（ID）」を読み取る
      ↓
4. 管理リスト上で、その背番号のデータを「削除予定」にマークする
      ↓
5. 【自動】直後のアプリの隙間時間に、マークを見たSwiftDataが
   データベース（SQLite）の該当データを完全に消去（オートセーブ）
      ↓
6. 【自動】データベースが書き換わったので、
   `@Query` がそれを検知して画面（List）からその行を消す

**自分の理解：**

自動と言えどこのリレーが働いており順を追って処理が行われると理解した。
またオートセーブ中にもエラーが発生する可能性はあり冗長になったとしても安全性を向上した方が良いと感じた。
